publication::handoff composes Publisher::reopen and existing Namespace commands.
Readonly planning pins both original publication IDs, exact original admitted
source Version, source revision, namespace identity and keeper snapshot. It never manufactures
custody from a label. Existing publication verification proves the released tree
contains exactly that candidate/output object. Full candidate identity/provenance
must agree at the keeper. A flat cohort may retain the exact member after its
original per-asset ingest claim is released. Same-pool ingest-to-cohort transfer
is also metadata-only. No case proves independent physical devices or grants
byte eviction authority.

Apply defaults denied. Before either new journal command, reopen the native
source publication and keeper original completion/settled accounting/bytes with
their physical/metadata/config/namespace guards. Publisher::reopen remains
unchanged: it refuses an unprotected original ingest. Only this handoff composes
its private observed completion with a separately verified retained snapshot.
Open the actual keeper roster root from its admitted profile, never a copied
namespace handle. Hold keeper snapshot source_use at its actual current
revision/full current Version, then verify the exact snapshot Version/member
still exists (current or retained predecessor). This guards the whole keeper source, including retained history.
Withdrawn-only keeper history without a current source-use generation refuses.
Old keeper namespaces return Unsupported; no implicit upgrade or weaker fallback.
Source and keeper snapshot may share a namespace/pool but cannot be the same
source slot. Report the original publication recovery minima and the separately
retained snapshot namespace minimum; do not interchange them.

If the original ingest Version is current, Withdraw it, preserving it as a hard
predecessor, then Retire that exact predecessor. If already a predecessor, Retire
only that Version; preserve newer current and all other history. Pending or stale
source revisions refuse. Object-use guards deliberately permit these metadata
mutations while preventing participating eviction. Keeper generation cannot be
withdrawn/retired by another participating writer until handoff finishes.

Commands have immutable operation IDs derived from the frozen handoff plan.
Persist that plan asset-side before apply. Status reads only original command
receipts and never asserts current custody. Interrupted Withdraw leaves hard
history and both copies intact. Apply/retry reopens fresh keeper custody before
any remaining effect, then reuses the original journal operations. Completed
historical retry returns original receipts without requiring either pool online;
it explicitly reports historical acknowledgement, not renewed custody.
If another writer changes the source revision between commands, retain history
and report Stale; do not withdraw the newer selection. Explicit replanning needs
original status and fresh retained proof. No timeout removes claims or bytes.

No media or metadata is deleted. Native eviction still needs the existing full
roster/job/shared-demand, physical-origin, independent-device, authority and
incarnation controller proofs. Git source selection/currentness and authenticated
worker orchestration remain additional requirements; this SDK entry alone does
not activate merge-to-eviction or qualify mixed legacy actors.

Consumers that require original Publisher::reopen must qualify retained-snapshot
access before their original source is released; this API does not rewrite
consumer recovery handles. The qualified REEL SDK pin is unchanged.
